# 代码审查

目标产出：`docs/deliverables/<slug>/04-code-review.md`。输入：`02-tech-design.md`（任务与验收方式）、`03-dev-log.md`（改了什么）、实际代码。

审查者独立于实现者（chief 审 general 写的代码）。**只给结论与证据，不改业务代码**；发现问题写进缺陷清单，退回 general 修复后复审。

## 审查清单（逐项判定，不通过必须写证据）

### 1. 正确性

- [ ] 每个 T 任务都能在代码里找到落点，没有漏做或做多
- [ ] 边界条件：空、0、超长、特殊字符、并发/重复提交已处理
- [ ] 异常分支：加载/错误/空态、网络失败、超时有明确处理，不是静默吞掉
- [ ] 类型正确：typecheck 通过，没有 `any` 逃逸、`@ts-ignore`、不必要的断言
- [ ] 排序/比较按值类型处理：数字用数值比较，字符串用文本比较，不能一律转字符串

### 2. 质量与设计

- [ ] 单一职责：模块/文件职责清晰，没有把业务语义塞进通用组件
- [ ] 接口兑现：类型声明的每种情况都有实现（声明了却没渲染 = 不通过）
- [ ] 状态身份稳定：Provider value、回调、返回值没有每次渲染重建导致无谓重渲染
- [ ] 没有死按钮、没有无 `onClick` 的交互元素（占位必须标 TODO 或不渲染）
- [ ] 通用组件只给中性默认值，业务文案/字段由调用方注入

### 3. 约定一致

- [ ] 命名与目录符合 `conventions.md` 第 7 节；barrel 只 re-export
- [ ] 每个目录 `README.md` 与实际文件清单、职责一致（`conventions.md` 第 9 节）
- [ ] 数据库变更有迁移文件、未用 `prisma:push`（第 5 节）
- [ ] 用官方 API / 组件，不重复手写；新引入技术有官网一手依据
- [ ] 注释与 README 说的行为跟代码一致（没有"配了没效果"的配置）

### 4. 验证证据

- [ ] typecheck / lint / build 真跑过，写清命令与结果
- [ ] 关键交互有手动或浏览器验证证据（路径 / 截图）
- [ ] 缺陷按 P0~P3 分级，写清 `文件:行号` 与复现方式

## 报告格式

```markdown
# <需求名> 代码审查报告

结论：通过 / 不通过（退回修复）/ 阻塞
审查范围：分支、提交号、文件清单

## 逐项判定
| 项 | 结论 | 证据（文件:行号 / 命令输出） |

## 缺陷清单
| 编号 | 等级 | 文件:行号 | 问题 | 修复要求 |

## 复审记录（如有）
首轮不通过项、修复后复测结果
```

## 判定纪律

- 只认证据，不认「应该没问题」；没跑的命令写「未执行」，不写「通过」。
- 结论「不通过」→ 退回 general 按缺陷清单修复，修复后复审原问题；同一问题两次不通过 → 升级给用户。
- 通过后才能派 qa；报告结论不是「通过」→ 门禁不放行。
