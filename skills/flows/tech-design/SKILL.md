# 技术方案模板

目标产出：`docs/deliverables/<slug>/02-tech-design.md`。输入是同 slug 的 `01-prd.md`，按其中的功能编号逐条对齐。

技术方案的第一道关不是画架构图，而是证明 PRD 里的每条功能都能落地。只要有一条「需调整」或「不可做」，就必须先回 PRD 修订再评审——把可行性疑问留给开发，是「产品拍脑袋、开发接不住」的根源。

## 文件结构

```markdown
# <需求名> 技术方案

## 1. 现状
相关模块现状、已有能力、受影响的调用方。

## 2. 可行性结论
逐条对照 PRD 功能编号：

| 功能 | 可行性 | 依据 | 若不可行的替代 |
| F1 | 可做 | 现有模块可直接扩展 | — |

只允许三种结论：可做 / 需调整 / 不可做。
出现「需调整」或「不可做」时，先回 PRD 修订对应功能或验收标准，修订后重新评审；不得带着未解决的可行性疑问继续写下面的方案。

## 3. 方案概述
一段话讲清怎么做；附 mermaid 架构图或流程图。

## 4. 技术选型
| 选项 | 结论 | 理由 | 被否原因 |
默认沿用项目现有选型；新引入的必须说明成本与替代方案。

## 5. 数据模型
表/集合、字段、类型、索引、唯一约束、迁移方式、历史数据兼容。

## 6. 接口契约
| 方法 | 路径 | 入参 | 出参 | 错误码 |
错误码要覆盖：参数错误、未授权、无权限、不存在、冲突、限流、内部错误。
写清幂等性、分页、时间格式、字段命名风格。

## 7. 模块与文件规划
新增/修改的目录与文件，每个文件职责一句话。禁止留「待定」。

## 8. 关键流程
主干流程 + 异常分支（超时、重试、并发、部分失败）的时序说明。

## 9. 安全与权限
鉴权方式、越权防护、敏感数据脱敏、输入校验位置。

## 10. 兼容与迁移
是否需要数据迁移、灰度、开关、回滚步骤。

## 11. 任务拆分
| 编号 | 任务 | 涉及文件 | 依赖 | 验收方式 |
T1..Tn，单个任务一次提交可完成。

## 12. 风险
风险 + 触发条件 + 应对措施。
```

## 任务拆分的硬标准

任务拆分是开发派单的依据，必须让执行者不用再问「这个任务具体改哪些文件、怎么算做完」。

- 一个任务只做一件事，改动文件可枚举。
- 任务之间依赖用编号写明，能并行的标注「可与 Tn 并行」。
- 每个任务都可独立验证：写清跑什么命令、看什么结果。
- 不出现「完善细节」「优化体验」这类任务。

## 自检清单

- [ ] PRD 每个功能编号都有可行性结论，且全部为「可做」
- [ ] PRD 每个功能编号都能在方案里找到落点
- [ ] 接口入参出参与 PRD 字段一一对应
- [ ] 有错误码表，且前端能据此给出提示
- [ ] 权限校验写在服务端，不只依赖前端隐藏
- [ ] 迁移与回滚可执行，不需要临时手工改库
- [ ] 任务清单总和 = 完整需求，无遗漏、无重复
